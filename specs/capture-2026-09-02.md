## 5. 缓存机制结论（核心，受控实验逐项证实）

### 5.1 基本事实

| 场景 | prompt_cache_hit_tokens | 结论 |
|---|---|---|
| 自定义 body，无 request-id 头，连发 3 次 | 0, 0, 0 | 复现 workbuddy-cliproxy 已知 bug |
| 自定义 body + request-id 三件套头，缓存温热期 | 320 | 共享前缀命中 |
| 官方系统提示词 + 无头 | 512 | 共享内容的边缘基础缓存（始终命中） |
| 官方系统提示词 + request-id 头 | 3200（后冷却至 512） | 完整共享缓存解锁 |
| 同一会话 + 相同自定义 body 连发 3 次 | 0→320→320 | 自定义内容本身**永不缓存**，只共享前缀命中 |
| 多轮增长历史（官方风格） | 320 恒定，miss 随历史增长 | 历史内容不缓存 |

### 5.2 机制模型

1. **上游 prompt cache 是"全局共享内容前缀缓存"**：缓存键与内容在全体请求中的共享度相关。codebuddy 官方系统提示词对全体用户相同 → 全局缓存，全量命中（3200）；服务器自身前置约 320 token 的共享系统前缀 → 恒定可命中；用户独有内容（自定义 system、对话历史）→ 从不缓存（官方客户端自己的独特内容同样 miss：首捕 hit=512 / prompt=8962）。
2. **request-id 头族是"官方身份开关"**：`X-Request-ID` + `X-Conversation-Request-ID` + `X-Conversation-Message-ID`（以及完整的 trace 头族）在场时，上游启用完整缓存服务/上报；缺失时仅边缘基础缓存（512）生效、且自定义内容共享前缀也不上报。
3. **缓存有 TTL**：温热期命中、冷却后归 0（同一请求在 10 分钟内从 320 变 0）。
4. 单 header 不生效（X-Request-ID 单独 / 两两组合均 0）；畸形值（33 字符）无效。

### 5.3 对 wb2api 的含义（诚实范围）

- ✅ 注入官方 trace/conversation 头族后，`prompt_cache_hit_tokens` 从恒 0 变为可命中（共享前缀 320 + 官方系统提示词 512/3200）
- ✅ 实测：wb2api 端到端（core+cmd/server）打真实上游，官方系统提示词 → hit=512，与官方客户端一致
- ❌ 无法让"每个用户的长对话内容"命中缓存——上游对独有内容不缓存（对官方客户端也不缓存）
- ⚠️ 缓存命中受 TTL 影响，非每次都报命中；验收标准应调整为"注入头后同内容命中率显著提升"，而非"恒命中"
